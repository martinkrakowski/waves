# Plan: `waves sync` — a pusher that keeps running

Owner, 2026-10-04: "the waves status page is not getting updates consistently
from the active session projects … how can we fix this", then "yes" to the
recommendation below.

Decisions continue the numbering of `2026-10-03_midnight-console.md` (W41 was
its last). Reviewed by Fable on 2026-10-04; its findings are folded in.

## 1. What is wrong

The server's log over about fourteen hours (2026-10-03 19:00Z to 2026-10-04
09:10Z, every `PUT` since the last deploy):

| Project          | Writes              | How it pushes today                                                                                                         |
| ---------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| campaign-foundry | 0                   | Has a real pusher (`tools/wave-status --push --watch`, its #651), but nothing keeps it running: last push 2026-10-02 19:20Z |
| hexagen-monaco   | 2 bursts, 5 h apart | Its session maps its event logs to lanes by hand after a milestone; each burst re-sent four waves and met one `429`         |
| client-portal    | 1                   | By hand                                                                                                                     |
| waves            | 1                   | By hand (the orchestrator's wave file)                                                                                      |

The contract assumes a pusher that runs: `intervalSeconds` is at most 300, and a
wave is stale once it has not been received for `min(3 × interval, 300)`
seconds (`docs/waves-v1.md` §4, `staleAfterMs` in
`packages/contract/src/domain/staleness.ts`). A wave pushed by hand once per
milestone is therefore stale five minutes later: every project reads stale,
every alive lane reads `unknown`, and the attention view fills with `silent`
lanes. Staleness — the one signal a witness has about a pusher — says nothing.

## 2. The fix

Every project gets a process that re-derives its waves and pushes them on a
timer, so that a fresh wave means "a pusher looked within the interval" and a
stale one means "the pusher, or the machine it runs on, stopped".

- **campaign-foundry** already has one. Its session runs it as a LaunchAgent
  (asked 2026-10-04; that repo and agent are its own).
- **Every other project** gets `waves sync`: one run of each configured
  project's own collector, and a paced push of what it printed. launchd is the
  timer.

## 3. Decisions

| #       | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **W42** | **`waves sync` runs once and exits; launchd is the timer.** A LaunchAgent (`cloud.krakowski.waves.sync`, `StartInterval` = the configured period, `RunAtLoad`) starts it. No loop, no sleep between ticks, no signal handling in the client. A crash costs one tick; a sleeping Mac lets every wave go stale; both are what the dashboard should then say. launchd never runs two copies of one label, so a run that outlasts its period makes launchd skip a fire — accepted, and bounded by W48.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **W43** | **The configuration is `sync.json` in the client's config directory** (`~/.config/waves/sync.json`, moved by `WAVES_CONFIG_DIR`): `{ "every": 60, "projects": [ { "project": "<id>", "command": ["/abs/path", "arg", …], "cwd": "/abs/dir", "timeoutSeconds": 20 } ] }`. `every` is an integer 10 to 100 (default 60) and is every pushed wave's and status's `intervalSeconds`, so a wave goes stale after `3 × every` seconds (≤ 300, under the contract's ceiling): it survives two missed ticks and goes stale on the third. 100 is the top because above it the 300 s ceiling is reached and a wave would turn stale between two healthy ticks. `project` is a project id, unique in the file; `command[0]` and `cwd` are absolute; `timeoutSeconds` is 1 to 30 and at most `every / 2` (default `min(20, every / 2)`). The file is read with the client's existing secret reader (`readSecret`, `infrastructure/fs.ts`: `O_NOFOLLOW`, then `fstat` on the open handle, a regular file, no group or other bits, nothing executable), with refusal messages worded for this file rather than for a token. A file that fails it, does not parse, or breaks a rule above: exit 2, nothing run.                                                                                                                                                                                                          |
| **W44** | **A collector is a program the project owns; the client runs it without a shell.** `spawn(command[0], command.slice(1), { cwd, env, detached: true, stdio: ["ignore", "pipe", "pipe"] })`, with its own process group: on the timeout the whole group is sent `SIGKILL`, so a grandchild holding the pipe cannot keep the run alive; the run then waits at most 1 s for the pipes to drain. Its environment is `PATH`, `HOME`, `LANG` and `WAVES_PROJECT` only — never `WAVES_URL`, never a token path, never the rest of the client's environment. stdout is capped at 4 MiB and stderr at 64 KiB, each counted separately; an over-long stdout is a failed collection (the group is killed).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **W45** | **The trust boundary is the owner's approval of `sync.json`, not the environment.** A collector runs as the owner's own user and could read `~/.config/waves/<project>.token` itself; file modes protect against other users, not against the owner's own programs. W44's environment keeps a collector from being _handed_ a credential by accident; what keeps credentials away from code nobody reviewed is that only the owner writes `sync.json` (W43's mode rule) and only names programs the owner trusts. The client reads the token itself, after the collector exits, as `push` does.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **W46** | **The collector's output** is one JSON object: `{ "waves": [ { "wave": "<id>", "lanes": [ … ] } ], "status"?: { … } }`. `lanes` is what `waves push --file` accepts (tails handled exactly as `push` handles them by default); `status` is what `waves status --file` accepts. At most 32 waves; a wave id that appears twice is an invalid output. A wave the collector does not print is not pushed and goes stale on its own — right, since nobody looked at it. Each wave and the status are validated as `push` and `status` validate them; an invalid wave is reported and skipped, the others are pushed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **W47** | **Every failure is that project's failure.** A collector that exits non-zero, times out, overflows, prints non-JSON or the wrong shape; a missing or unreadable token; a push or status that fails after its retries: one line on stderr, `waves sync: <project>: <reason>` (any collector stderr included is cut to one line of 200 characters with control characters removed, and no token value can appear in it), and the next project runs. Nothing is pushed for a project whose collector failed — not an empty wave, not a stale "alive". The run exits 1 if any project failed, 0 otherwise; on success it writes one stdout line per project (`waves sync: <project>: N waves`), so the log grows by a few lines a minute — the LaunchAgent's log is rotated by `newsyslog` or truncated by `install.sh`, whichever the S2 lane finds simplest, and says which.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **W48** | **Pacing and time.** Every write attempt for one project — a first try or a retry inside `sendIdempotent` — waits until 1 s has passed since that project's previous attempt, through a paced transport wrapped around the real one (so a `Retry-After: 0` or an elapsed date cannot send two requests in the same second). Writes are therefore spaced 1 s apart before they are sent (the server allows one write a second per project: `PROJECT_INTERVAL_MS` in `packages/server/src/application/limiters.ts`; `register-all` spaces its own the same way, `REGISTER_SPACING_MS`), so a healthy tick sends no request a `429` answers; `Retry-After` handling stays as the safety net. Projects run one after another, under one hard budget of `every` seconds of wall time for the whole run: a collector is given `min(timeoutSeconds, what is left)`, a project stops sending further waves once the budget is spent (`waves sync: <project>: out of time after N waves`), and every project not yet started is reported `skipped, out of time`. `timeoutSeconds` may be at most `every / 2`, so one collector can never take the whole tick. **Fairness without state:** each run starts at project index `floor(now / every) mod n` and wraps round, so a slow project costs the ones after it a tick, and the order moves on at the next tick rather than starving the same project every time. |
| **W49** | **The shared send path.** What `push.ts` and `status.ts` do after reading their input — build the document, validate it, build the request, `sendIdempotent`, `readReceivedAt` — becomes one function per document kind that takes the project id and the token as arguments (today `readProjectToken` in `session.ts` takes the project from `WAVES_PROJECT`). `push` and `status` call it unchanged in behaviour; `sync` calls it per project. `sendIdempotent`'s label (`"push" \| "status"`) and the CLI's command names gain `sync`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **W50** | **The LaunchAgent** is a template in `deploy/launchd/`, rendered by `install.sh` (removed by `uninstall.sh`) when `sync.json` exists, with `WAVES_URL`, `WAVES_CONFIG_DIR` and `PATH` in its environment — `PATH` because launchd's default is `/usr/bin:/bin:/usr/sbin:/sbin` and a collector that calls `node` or `gh` from Homebrew or nvm would fail under the agent and pass by hand. `install.sh` takes the `PATH` it is run with, under its existing quoting rule. `StartInterval` and `ThrottleInterval` are both `every`. Nothing in the plist holds a token.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **W51** | **Collectors are written by each project's own session**, in its own repo, to W46's shape; waves holds no project vocabulary (console plan W12). For a project with no derivation, the smallest collector prints the orchestrator's hand-kept wave files, and must drop `alive: true` from any lane whose file is older than `every`, so a forgotten file reads `unknown` rather than alive. A generic collector for lanes on midnight's opencode is §6, not this plan.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## 4. Lanes

### S1a-send-path (normal), the refactor

W49 only, in `packages/client`: extract the per-document send function, make
`push` and `status` use it, add `sync` to the label and command-name types. Every
existing client test passes unmodified; new unit tests only for the extracted
function's project/token parameters. No behaviour change.

### S1b-sync (high), after S1a

`waves sync` per W42–W48 in `packages/client`: the argument, the config reader on
`readSecret`, a process-runner port with its Node adapter (W44), the use case,
README, and a short "Keeping waves fresh" section in `docs/waves-v1.md`. Tests:
config refusals (symlink, group/other bit, executable bit, bad `every` including
101, relative `command[0]` or `cwd`, duplicate project); collector failures (exit,
timeout, a grandchild holding the pipe past the timeout, stdout overflow, stderr
overflow kept as a cut line, non-JSON, wrong shape, 33 waves, a duplicate wave
id); one invalid wave among valid ones; the collector's environment (no
`WAVES_URL`, no token path, `WAVES_PROJECT` set); a missing token failing only
that project; pushes spaced 1 s apart, and a `429` then `200` across two waves;
`every` written as `intervalSeconds` on waves and status; the out-of-time skip;
exit codes; and the no-leak pattern of `no-leak.test.ts`: no token value in any
stderr line, including when a collector fails. Mutations: the environment leaking
`WAVES_URL`; a failed collector still pushing; the mode check bypassed; the wave
cap removed; the process-group kill replaced by a child-only kill.

### S2-launchd (normal), after S1b

W50: the plist template, `install.sh`/`uninstall.sh`, log handling, and their
tests (`packages/server/__tests__/launchd.test.ts` pins the register-all
template's rendering today).

### Rollout (orchestrator)

1. Publish the client (`@hexagen-monaco/waves-client`, minor bump; the owner
   publishes).
2. Install the agent with a `sync.json` holding the `waves` project's own
   collector.
3. Message every live session (campaign-foundry-74, hexagen-monaco-8e,
   krakowski-cloud-client-portal): the collector shape, how to add a
   `sync.json` entry (the owner adds it; W45), and that hand pushes can stop
   once theirs is in.
4. Check the server log: one write per wave per period from each configured
   project, spaced, with no `429`.

## 5. Risk

`sync.json` names programs a background agent runs every minute as the owner.
The controls are W43's file rule and W45's review: only the owner writes the
file, and it names only programs the owner trusts. W44's environment and the
absence of a shell are hygiene on top. The service's side is unchanged: a
collector's output is validated by the contract before it is sent, and again by
the server.

## 6. Not in this plan

| Candidate                           | Note                                                                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A generic opencode-lane collector   | Liveness from opencode's database (`lane-usage`), commits from the worktree, PRs from `gh`. Every project here runs lanes on midnight; its own plan once S1b ships. |
| Raising the 300 s staleness ceiling | The ceiling is right once pushers run; raising it would hide stopped pushers for longer.                                                                            |
| A long-running `waves watch` loop   | launchd already is the loop (W42).                                                                                                                                  |
